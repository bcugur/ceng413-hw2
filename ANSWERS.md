## 1. Service Discovery by Name
When Docker Compose starts our multi-container application, it automatically creates a user-defined bridge network equipped with an embedded DNS server listening at `127.0.0.11`. When the `app` container sends a network request to `cache`, Docker's internal DNS intercepts the query and automatically translates the service name into the dynamic private IP address assigned to the Redis container. In contrast, containers started with standard `docker run` without a custom network join the default `bridge` network, where automatic DNS resolution by container name is disabled by design for legacy backward compatibility. On that default bridge network, containers cannot discover each other by hostname and can only communicate via raw IP addresses or deprecated `--link` flags, causing name lookups to fail with "bad address" errors.

## 2. Stateless vs. Stateful Services and Experimental Evidence
In our architecture, the `app` service is completely stateless because it never writes persistent data to its own container filesystem, while the `cache` (Redis) service is stateful because its append-only data files are persisted into the named Docker volume `redisdata`. We proved that `app` is stateless by calling `/visit` multiple times, forcefully removing the app container with `docker compose rm -sf app`, and then recreating it with `docker compose up -d app`; upon invoking `/visit` again, the counter continued incrementing from where it left off rather than resetting. We then demonstrated the persistence of the stateful `cache` service by executing `docker compose down` followed by `docker compose up -d`; because Docker keeps named volumes when shutting down, the counter once again preserved its count across total container recreation. Finally, when we executed `docker compose down -v` to explicitly delete the named volume, the next `docker compose up -d` started with a fresh volume and the counter reset back to 1, proving that all state resided exclusively in the volume.

## 3. Secret Management and Why Passwords Belong Outside Git
A database password should never be hardcoded into source code or Compose files; instead, it should be injected at runtime via environment variables, an uncommitted `.env` file excluded by `.gitignore`, Docker secrets, or a dedicated secrets manager like HashiCorp Vault or AWS Secrets Manager. Committing passwords to Git is dangerous because version control preserves an immutable, permanent commit history that is duplicated to every collaborator's local workstation, build agent, and repository clone. Even in a private repository, credentials can easily be compromised through leaked personal access tokens, misconfigured repository permissions, compromised developer laptops, or accidental changes that make the repository public. Furthermore, hardcoding secrets in Git violates Twelve-Factor App principles by tightly coupling code to a single environment, preventing secure credential rotation and making it impossible to safely reuse the same image across development, testing, and production.
